1. Escopo e ASP.NET Identity

using (var scope = app.Services.CreateScope())
{
    var roleManager = scope.ServiceProvider
        .GetRequiredService<RoleManager<IdentityRole>>();

    var userManager = scope.ServiceProvider
        .GetRequiredService<UserManager<ApplicationUser>>();
}
ElementoResponsabilidade
scopeCria um escopo temporário para usar dependências de vida curta durante o startup.
RoleManagerConsulta, cria, atualiza e remove roles.
UserManagerConsulta e administra usuários, senhas e associações com roles.
usingChama Dispose() ao final e libera recursos do escopo de modo determinístico.
Precisão: using não “limpa a memória”. O Garbage Collector administra a memória comum. O Dispose() encerra corretamente recursos como o contexto e conexões relacionadas ao banco.

2. Criação segura das roles

foreach (var role in new[] { adminRoleName, "Barbeiro", "Cliente" })
{
    if (!await roleManager.RoleExistsAsync(role))
    {
        var result = await roleManager.CreateAsync(
            new IdentityRole(role));

        if (!result.Succeeded &&
            !await roleManager.RoleExistsAsync(role))
        {
            throw CreateIdentityException(result);
        }
    }
}
Role já existe?↓ Não → tenta criar↓ Criação falhou?↓ Verifica novamente antes de concluir que houve falha real

A segunda consulta protege contra uma corrida: duas instâncias podem observar a ausência da role e tentar criá-la quase simultaneamente. Uma vence; a outra recebe erro de duplicidade, verifica novamente e percebe que a role agora existe.

Importante: await espera aquela operação terminar. A segunda verificação não existe porque o primeiro método “ainda está executando”, mas porque outra instância da aplicação pode atuar ao mesmo tempo.

3. Usuário existente e elevação de privilégios

var admin = await userManager
    .FindByEmailAsync(bootstrapAdminEmail!);

if (admin is not null &&
    !await userManager.IsInRoleAsync(admin, adminRoleName))
{
    throw new InvalidOperationException(
        "BootstrapAdminExistingUserIsNotAdmin");
}
Estado encontradoDecisão
Conta não existeO bootstrap pode criar a conta inicial.
Conta existe e já é AdminEstado esperado; operação idempotente.
Conta existe sem AdminFalha e exige investigação humana; nunca promove automaticamente.

Promover automaticamente uma conta apenas porque seu email coincide com a configuração poderia transformar um cliente, barbeiro ou conta comprometida em administrador.

4. Criação do usuário e os dois significados de !

var createResult = await userManager.CreateAsync(
    newAdmin,
    bootstrapAdminPassword!);

if (!createResult.Succeeded)
{
    // tratar falha
}
SintaxeSignificado
bootstrapAdminPassword!Operador de supressão de nulabilidade. Apenas diz ao compilador para confiar que o valor não é nulo.
!createResult.SucceededNegação booleana executada em runtime: transforma true em false e vice-versa.
O operador pós-fixo não valida: se a senha realmente fosse null, o ! não criaria um valor nem impediria falhas. A validação real ocorreu antes, em GetRequiredConfiguration.

CreateAsync valida o usuário e a senha, cria o hash, persiste a conta e devolve um IdentityResult com sucesso ou códigos de erro.

5. Duplicidade e retry de concorrência

var errors = result.Errors.ToArray();

return errors.Length > 0 &&
    errors.All(error =>
        error.Code is "DuplicateEmail" or "DuplicateUserName");

O retry só é permitido quando existe pelo menos um erro e todos são duplicidades. Uma falha mista, como DuplicateEmail junto de PasswordTooShort, não é concorrência pura e deve interromper o startup.

Dez consultas, nove esperas

const int maximumAttempts = 10;
var retryDelay = TimeSpan.FromMilliseconds(100);

São feitas até dez consultas, mas somente nove intervalos de 100 ms. Após a décima consulta não existe nova tentativa, portanto esperar outra vez seria inútil.

O método retorna sucesso apenas quando:

concurrentAdmin is not null &&
await userManager.IsInRoleAsync(
    concurrentAdmin,
    adminRoleName)

As condições estão ligadas por &&: o usuário precisa existir e já possuir a role Admin. O processo perdedor observa; nunca promove.

6. Compensação de estado parcial

if (!addToRoleResult.Succeeded)
{
    var cleanupResult =
        await userManager.DeleteAsync(newAdmin);

    throw cleanupResult.Succeeded
        ? CreateIdentityException(addToRoleResult)
        : CreateIdentityException(
            addToRoleResult,
            cleanupResult);
}
Usuário foi criado↓ Adicionar Admin falhou↓ Tenta apagar o usuário↓ Em todos os casos, o startup falha

Se a limpeza funcionar, o banco volta a um estado sem a conta parcial. Se falhar, pode permanecer um usuário sem a role Admin, exigindo inspeção manual.

Compensar não significa concluir: apagar o usuário repara o estado parcial, mas o administrador inicial ainda não foi criado. Por isso, a inicialização falha mesmo quando o cleanup funciona.

7. Mensagens de erro seguras

var errorCodes = string.Join(", ", results
    .SelectMany(result => result.Errors)
    .Select(error => error.Code));
  • params permite receber um ou vários IdentityResult.
  • SelectMany reúne os erros de todos os resultados.
  • Select extrai apenas cada Code.
  • string.Join produz uma mensagem curta e objetiva.

As descrições não são usadas porque podem mudar, ser localizadas ou ser produzidas por um provider personalizado. O objetivo é diagnosticar usando códigos sem expor senha, email ou detalhes desnecessários.

8. Testes em resumo

Não é necessário decorar cada teste. Eles registram o contrato que a implementação deve preservar:

  • Bootstrap ausente ou desabilitado não cria usuário.
  • Configuração inválida causa fail-fast sem revelar valores.
  • Configuração válida cria o administrador com a role correta.
  • Conta existente sem Admin não é promovida.
  • Execuções repetidas não duplicam a conta.
  • Falhas do Identity divulgam apenas códigos seguros.
  • Falha ao adicionar a role aciona a compensação.
  • Concorrência termina de maneira limitada e nunca promove o usuário observado.

Estrutura mental suficiente:

Arrange → preparar configuração e estado
Act     → inicializar a aplicação
Assert  → verificar o comportamento esperado

9. Quiz interativo

Escolha uma opção em cada questão. A explicação aparece imediatamente.

Pontuação: 0/0

1. Qual componente cria e verifica as roles?

O RoleManager administra as roles. O UserManager administra usuários e suas associações.

2. O que o using faz com o escopo?

O using garante Dispose(). A memória comum continua sendo responsabilidade do Garbage Collector.

3. Por que verificar novamente se a role existe após uma falha de criação?

O await espera. A segunda consulta trata uma possível corrida entre instâncias.

4. Uma conta existente com o email configurado não possui Admin. O que fazer?

A promoção automática seria elevação de privilégios. O bootstrap falha de forma conservadora.

5. O que significa bootstrapAdminPassword!?

O operador pós-fixo informa confiança ao compilador; a validação real ocorreu antes.

6. Um resultado possui DuplicateEmail e PasswordTooShort. Deve iniciar retry?

errors.All(...) exige somente erros de duplicidade. Esperar não corrige uma senha inválida.

7. Dez consultas com nove intervalos de 100 ms produzem qual espera planejada?

Não há espera após a última consulta: 9 × 100 ms = 900 ms. As consultas também consomem tempo.

8. Quando o retry concorrente retorna true?

As condições usam &&: o usuário precisa existir e já estar na role Admin.

9. A limpeza funcionou após a falha de AddToRole. O startup deve continuar?

A compensação evita o estado parcial, mas o administrador não foi criado. O startup deve falhar.

10. Por que registrar apenas error.Code?

Os códigos são suficientes para o diagnóstico esperado. Descrições podem mudar ou conter detalhes desnecessários.

Resumo de bolso

Abrir resumo em dez frases
  1. O escopo permite usar corretamente dependências de vida curta no startup.
  2. RoleManager administra roles; UserManager administra usuários.
  3. O using garante a liberação determinística do escopo.
  4. Uma segunda consulta diferencia falha real de corrida entre instâncias.
  5. Conta existente sem Admin nunca é promovida pelo bootstrap.
  6. O ! pós-fixo não valida valores; apenas silencia a nulabilidade.
  7. O retry só aceita falhas compostas exclusivamente por duplicidades.
  8. O concorrente precisa existir e já possuir Admin.
  9. Falha de role tenta compensar removendo o usuário recém-criado.
  10. Mensagens expõem códigos, não senhas ou descrições desnecessárias.
