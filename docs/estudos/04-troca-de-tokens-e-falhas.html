Troca de tokens: nosso próximo contrato

05/10/2026 — Histórico RED: 16 casos, 14 falhas esperadas e 2 aprovados. Após aprovação e testes de armazenamento, troca e persistência protegida foram implementadas: GREEN da solução com PostgreSQL, 125 aprovados. Nenhuma conta real foi conectada. Continue no estudo 05 para entender proteção e limites.

Código não é access token

O código recebido pelo callback é uma autorização temporária. O servidor o apresenta ao provedor com client_id, client_secret, redirect_uri e verifier PKCE. O provedor pode retornar access_token, refresh_token, expires_in e user_id.

Esses valores nunca vão para o navegador. O servidor deve validar a resposta e proteger as credenciais antes de declarar a conta conectada.

Fluxo esperado: state válido → consumo único → troca externa → validação → armazenamento protegido → Conectado. Uma falha interrompe essa sequência.

Como provar o PKCE?

O teste guarda o challenge da URL de autorização. Depois captura o verifier enviado ao provedor simulado e calcula Base64URL(SHA256(ASCII(verifier))). O resultado deve ser exatamente o challenge original: não basta enviar qualquer texto com 43 caracteres.

Simulação HTTP não é sandbox real

O handler de teste responde dentro do processo, sem abrir conexão com o Mercado Pago. Ele captura método, URL e JSON usando apenas valores fictícios.

Sandbox real usa aplicação e contas de teste no provedor. O payload proposto envia test_token=true, mas estes testes não validam conectividade, credenciais reais, consentimento ou compatibilidade de produção. Esses passos só vêm após proteção e persistência.

Erros fazem parte da especificação

Falha HTTP do provedor: 502 com título seguro. Resposta incompleta ou inválida: 502 com outro título seguro. Timeout: 503. O body recebido não deve ser reproduzido para o cliente.

Não repetimos automaticamente a troca: o provedor pode ter consumido o código antes de a resposta se perder. Para tentar novamente, o administrador inicia uma nova autorização.

A conexão agora é habilitada por configuração, preservando o comportamento anterior quando desabilitada. As expectativas dos 16 testes foram preservadas.

O que ainda falta testar?

Persistência protegida e falhas de gravação/proteção/driver já possuem testes. Ainda faltam recuperação operacional das chaves, concorrência ao substituir uma conta, renovação, desconexão e auditoria de instrumentação futura. Não é aceitável retornar Conectado somente porque o HTTP externo respondeu 200.

Exercícios com respostas

1. Por que o client_secret fica no body enviado pelo servidor?

É uma credencial privada da aplicação usada para a troca. Não deve aparecer na URL de autorização, no frontend, nos logs ou no repositório.

2. Como o teste descobre um verifier incorreto?

Recalcula seu SHA-256 em Base64URL e compara com o challenge da tentativa. Tamanho e formato corretos, sozinhos, não demonstram que ele pertence àquela tentativa.

3. Um HTTP 200 com body vazio comprova conexão?

Não. É preciso validar tokens, tipo, identificador e validade, depois armazenar as credenciais com proteção. Nosso teste rejeita a resposta vazia.

4. Por que state desconhecido deve produzir zero chamadas?

Sem uma tentativa válida, não existe autorização para trocar o código. Validar antes de contatar o provedor também reduz abuso e custo.

5. Por que não repetir automaticamente após timeout?

Não sabemos se o provedor consumiu o código. Um retry cego pode falhar ou causar inconsistência; o fluxo conservador exige iniciar outra autorização.

6. Os testes em RED são um bug introduzido na API?

Não neste incremento: só adicionamos especificações do comportamento futuro. A implementação atual não foi alterada. A nova suíte deve ficar verde antes de concluir essa feature.
