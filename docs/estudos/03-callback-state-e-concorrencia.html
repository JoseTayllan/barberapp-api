Callback seguro: reconhecer e consumir uma tentativa

Este capítulo registra o GREEN do callback: 95 testes aprovados, zero falhas/ignorados. Ajuste OpenAPI aprovado pelo mantenedor. O incremento posterior chegou a 125 testes; veja o capítulo 5. Não houve conexão com conta real.

Por que o callback não pede JWT e API key?

O provedor redireciona o navegador para a API sem nossos headers. A exceção é restrita ao GET da rota callback. A criação da tentativa continua exigindo Admin autenticado e API key. O retorno deve apresentar o state aleatório que o servidor associa à tentativa desse administrador. Não confiamos em um adminId enviado na URL.

O state é uma capacidade temporária: quem o possui pode apresentar o retorno. Não compartilhe URLs OAuth nem registre seus parâmetros. O callback não autentica um novo usuário nem concede role.

Consultar e remover: por que precisa de lock?

Sem sincronização, duas requisições podem consultar a mesma tentativa antes de qualquer uma removê-la. Ambas seriam aceitas. O lock envolve consulta, comparação e remoção. Somente uma pode consumir a tentativa.

O serviço é singleton: todas as requisições nesta instância compartilham o mesmo lock. Isso não sincroniza servidores diferentes. A memória é temporária e o reinício perde as tentativas.

Uma nova tentativa do mesmo administrador remove a anterior. Administradores diferentes possuem contextos separados. O relógio injetado permite testar exatamente o limite de dez minutos, sem esperar dez minutos reais.

Recusa não é erro inesperado

Uma tentativa válida com error=access_denied retorna AutorizacaoRecusada e é consumida. Parâmetros conflitantes ou repetidos são rejeitados. As mensagens não reproduzem os valores recebidos.

Com a conexão desabilitada, código válido retorna 503, MercadoPagoTrocaTokenPendente. No incremento posterior, quando habilitada e configurada, troca de tokens e gravação protegida precisam concluir antes do retorno Conectado. Isso não prova cobrança nem integração com uma conta real.

O teste também pode especificar a representação errada

O objetivo é documentar que o callback não exige API key ou Bearer. O teste exige literalmente security: []. O serializador omite a coleção vazia, herdando a regra global. A especificação OpenAPI também admite um requisito vazio: security: [{}].

Não removemos a asserção para conseguir verde. O mantenedor aprovou o ajuste: agora verificamos exatamente um requisito vazio, preservando as asserções de API key e Bearer na autorização. Os 95 testes passaram após a alteração.

Exercícios com respostas

1. O que impede um retorno de promover alguém a Admin?

O callback não cria usuários nem altera roles. Ele só reconhece uma tentativa que foi iniciada por Admin autenticado. O vínculo vem do contexto no servidor, não de um identificador informado no retorno.

2. Por que não basta remover a tentativa depois da consulta?

Outra requisição pode consultar no intervalo entre leitura e remoção. Precisamos tornar a sequência indivisível, com lock compartilhado nesta instância.

3. Com oito retornos concorrentes da mesma recusa válida, quantos são aceitos?

Exatamente um recebe 200; os outros sete recebem 400. Esse comportamento tem teste HTTP.

4. O instante igual à expiração é válido?

Não. A regra usa expiração menor ou igual ao instante atual para rejeitar. Testamos dez e onze minutos usando TimeProvider controlado.

5. Pode registrar a URL completa para depurar?

Não. A query pode conter state e código de autorização. O código novo não cria logs; a configuração atual restringe Microsoft.AspNetCore a Warning. Proxies, hospedagem e futura instrumentação também precisam redigir essas queries.

6. É correto apagar o teste Swagger que falhou?

Não. Primeiro identificar a diferença entre comportamento e representação. Aqui a proposta mantém a garantia e usa outra representação válida da especificação, com revisão explícita antes de mudar o teste.
