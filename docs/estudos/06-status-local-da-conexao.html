Consultar não é conectar nem cobrar

05/10/2026 — Implementado após aprovação dos testes, sem alterá-los. RED: 13 falhas e três aprovações; GREEN: 141 aprovados na solução, incluindo PostgreSQL. Build e formatação do recorte aprovados. Diff aguarda revisão final; pagamentos reais continuam desativados.

A pergunta do painel administrativo

O dono quer saber se há uma conta Mercado Pago cadastrada e se o prazo do token registrado já acabou. A proposta é GET /api/integracoes/mercado-pago/status, somente com API key e JWT Admin identificado.

A conta pertence à instalação. Outro Admin autorizado pode consultar a mesma conta; não filtramos pelo Admin que iniciou a conexão.

Um contrato pequeno, sem credenciais

{
  "status": "NaoConectado",
  "contaId": null,
  "expiraEm": null,
  "sandbox": null
}

São exatamente quatro campos. Com registro, o status é Conectado se expiraEm > agora UTC; caso contrário, Expirado. ContaId, expiração e sandbox continuam presentes mesmo quando expirada.

Nem token, ciphertext, senha ou identificador do Admin de origem pertencem à resposta. Cache-Control no-store impede armazenar a resposta em caches que respeitam esse header.

O que Conectado NÃO prova

Este status é local: não garante que o provedor ainda aceite o token. Uma revogação remota pode acontecer antes da expiração registrada. A consulta não testa a integridade do conteúdo protegido, não renova e não habilita pagamentos.

Como não precisa do token, não deve descriptografá-lo nem fazer chamadas externas. Nos testes, um payload opaco fictício não pode ser aberto e a factory HTTP lança erro se alguém tentar usá-la.

TDD e limites exatos

Um relógio fixo permite testar um segundo antes, exatamente na expiração e um segundo depois, sem esperar tempo real. Expiração igual ao instante da consulta já significa Expirado.

O RED obtido foi correto: o endpoint ainda não existia e retornava 404, em vez dos status esperados. O Swagger também não conhecia a rota. API key ausente/inválida já era barrada pelo middleware, por isso esses dois casos passaram antes da implementação.

O terceiro caso aprovado verifica a fixture: falha simulada somente na consulta da entidade de conexão, não nas roles do startup. Isso separa problema do ambiente de comportamento ausente.

Como a implementação foi dividida

Controller verifica o identificador do Admin, define no-store e traduz a falha para HTTP. Serviço consulta os metadados e compara expiração com TimeProvider.GetUtcNow. Repositório usa AsNoTracking e Select para buscar somente conta, expiração e sandbox.

O contrato de leitura é separado do de gravação, preservando os consumidores existentes. MetadadosConexaoMercadoPago não é uma entidade persistida: é uma projeção imutável, sem tokens, sem tabela e sem migration nova. O DTO da Application define os quatro campos públicos.

Os mesmos 16 testes passaram sem mudanças. A suíte completa inclui o teste PostgreSQL anterior de migration/constraint; o HTTP deste endpoint foi testado com InMemory, não com PostgreSQL. Conhecer esse limite evita prometer mais cobertura do que existe.

Exercícios com respostas

1. Por que uma conta expirada retorna 200 e não 401?

Porque o Admin foi autenticado corretamente. Expirado é estado da conexão Mercado Pago, não falha na autenticação do usuário.

2. Por que sandbox é null sem conta, em vez de false?

False indicaria uma conta de produção. Null expressa ausência de conexão e evita inventar um ambiente.

3. Uma API key válida basta para ler os metadados?

Não. Ela identifica o consumidor; a rota também exige JWT com role Admin e identificador de usuário.

4. Precisamos abrir o ciphertext para mostrar a expiração?

Não. A expiração já é um metadado separado. Descriptografar sem necessidade amplia a exposição e a dependência de chaves.

5. Se o banco estiver indisponível, podemos responder NaoConectado?

Não. Isso confundiria ausência de dados com falha de consulta. O contrato proposto retorna 503 MercadoPagoConsultaFalhou, sem detalhes internos.

6. Os 125 anteriores verdes significavam suíte completa verde?

Não. Aquela execução excluiu explicitamente os 16 novos casos. Depois da aprovação e implementação, uma execução sem esse filtro confirmou 141 aprovados e nenhum ignorado. Sempre confira os filtros e o total.
