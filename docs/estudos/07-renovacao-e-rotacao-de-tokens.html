Renovar não é repetir o login

19/10/2026 — Implementado após aprovação dos testes. RED: 26 falhas e dois aprovados; GREEN dos mesmos 28, sem alterá-los. Suíte completa com PostgreSQL isolado: 169 aprovados, zero falhas/ignorados; build e lint do recorte aprovados. Diff aguarda revisão final; nenhuma conta real ou cobrança.

Duas credenciais, funções diferentes

O access token permite acessar recursos do provedor. O refresh token permite solicitar novas credenciais sem repetir a jornada de autorização do navegador, quando a permissão concedida permite isso.

O Mercado Pago documenta rotação também do refresh token e autorização offline_access. Precisamos proteger e substituir os dois valores. O modelo atual não guarda scopes; o consentimento precisa ser validado no sandbox real, não presumido por um teste simulado.

Contrato implementado

POST /api/integracoes/mercado-pago/renovacao, com API key e JWT Admin identificado. Não enviar tokens no body: o servidor usa a conta da instalação e abre o payload protegido com o propósito correto.

Solicitação remota: URL fixa, grant_type refresh_token e credenciais privadas. Não reutilizar o authorization code nem o verifier do callback. Configuração sandbox deve coincidir com o registro; não migrar implicitamente credenciais entre ambientes.

Sucesso retorna somente os mesmos quatro metadados do status local, com no-store. O servidor só diz Conectado depois de proteger e gravar os novos tokens. Uma renovação não pode trocar silenciosamente a conta recebedora.

O intervalo perigoso

Imagine que o provedor já emitiu tokens novos, mas o banco ficou indisponível. A aplicação deve retornar falha, sem inventar sucesso ou salvar plaintext. Porém manter o registro antigo não desfaz o que aconteceu no provedor.

Por isso os testes exigem ausência de retry automático, mas não certificam recuperação operacional. Pode ser necessária nova autorização. Concorrência entre renovação, reconexão e futura desconexão também precisa de testes antes de pagamentos reais.

Como ler os testes

Cenario é a fixture: banco InMemory com nome estável por caso, provider criptográfico efêmero, relógio fixo e handler HTTP falso. Valores ONLY-FOR-TESTS não são credenciais reais.

Nos cenários válidos, a asserção abre o conteúdo salvo para conferir ambos os novos tokens e exige falha com outro propósito. Nos cenários de erro, confere que ciphertext, conta, Admin, sandbox e expiração anteriores foram preservados. Também conta chamadas remotas para detectar retry.

No RED, as falhas recebiam 404 porque a rota não existia. Dois casos já passavam pelos bloqueios de API key. Depois da aprovação e implementação, os mesmos 28 passaram sem mudanças. O teste PostgreSQL da suíte cobre armazenamento/migration/constraint anteriores, não todo o HTTP novo contra esse banco.

Como o código foi dividido

Controller autoriza, verifica identificador e traduz as respostas HTTP. RenovacaoMercadoPagoService valida configuração, abre somente o refresh necessário, confere a conta da resposta, protege os novos tokens e aguarda a gravação.

ICredenciaisConexaoMercadoPagoRepository lê a entidade protegida sem tracking. É um contrato distinto da consulta de status, que continua trazendo somente metadados. Não criamos tabela nem migration nova.

MercadoPagoOAuthClient agora compartilha transporte e validação estrutural entre o callback e a renovação. O payload depende do grant; apenas refresh trata invalid_grant como necessidade de nova autorização. Os testes antigos continuam cobrindo o callback.

Scoped significa uma instância por escopo; não significa lock entre requisições. Ainda precisamos coordenar operações simultâneas e planejar recuperação quando o provedor rotaciona antes de uma falha local. Este incremento não torna pagamentos reais seguros por si só.

Exercícios com respostas

1. Posso guardar só o access token novo?

Não. O refresh token também é rotacionado. A próxima renovação deve usar o valor retornado na última operação bem-sucedida.

2. Por que não devolver o refresh token ao Admin?

Porque o Admin precisa comandar a operação, não carregar a credencial. O servidor a usa e protege; o navegador recebe somente metadados.

3. Outro user_id na resposta pode substituir a conta?

Não. Renovar significa manter a identidade recebedora. O teste exige rejeitar essa resposta sem substituir o registro.

4. Timeout significa que o provedor não fez nada?

Não. A resposta pode ter se perdido depois do processamento. Repetir automaticamente uma operação de rotação pode piorar o estado; reconciliação ainda precisa ser projetada.

5. Preservar o banco antigo garante recuperação?

Não. Preservação local evita corrupção, mas não garante validade remota. Provedor e banco não participam de uma transação única.

6. Por que 409 para invalid_grant e 502 para outra falha remota?

É o contrato aprovado do BarberApp: invalid_grant sinaliza necessidade de nova autorização; falha genérica do provedor não deve ser confundida com isso. O body remoto nunca é copiado para o usuário.
