Estudo 02: conectar a conta do dono

Uma barbearia por instalação, uma conta recebedora e nenhuma divisão automática entre profissionais.

Este capítulo registra o primeiro incremento: início da autorização após RED válido no WSL (14 falhas esperadas, 1 aprovado), seguido de 74 testes aprovados. Callback e armazenamento protegido foram implementados depois; veja o capítulo 5. Cobrança real continua pendente.

OAuth: autorizar acesso

O dono acessa a página oficial do Mercado Pago e autoriza o BarberApp. Ele informa sua senha ao provedor. Nossa API recebe um código temporário e o troca, no servidor, por tokens de acesso.

Conectar a conta define quem recebe. Abrir o Checkout Pro define como o cliente paga. São fluxos distintos.

State: identificar a tentativa

A API gera um valor aleatório por tentativa. Quando o provedor retorna, o callback precisa demonstrar que aquele retorno corresponde a uma solicitação válida, ainda não expirada e não utilizada.

Não basta aceitar qualquer code recebido. Isso pode vincular uma conta diferente da que o administrador pretendia conectar.

PKCE: proteger a troca do código

O servidor guarda um segredo temporário chamado verifier. Na URL de autorização envia somente o challenge: SHA-256 do verifier, codificado em Base64URL. Na troca do código, apresenta o verifier original.

O verifier não deve aparecer na resposta enviada ao navegador nem na URL OAuth. PKCE complementa state; eles protegem aspectos diferentes do fluxo.

Quem pode conectar?

API key identifica o consumidor; JWT identifica o usuário; role Admin permite a ação. O identificador do usuário associa a tentativa a quem a iniciou.

O endpoint proposto devolve URL e expiração. Ele não devolve tokens nem confirma que a conta já foi conectada. O cabeçalho no-store evita cache da resposta sensível.

Checkout e confirmação

O cliente será levado ao Checkout Pro para escolher entre os meios disponíveis. O valor deve vir do agendamento no banco. Uma tela de sucesso não é comprovação suficiente: o servidor deve verificar o estado com o Mercado Pago.

Sandbox usa recursos de teste. Os testes automatizados usam respostas controladas e não cobram dinheiro real.

Exercícios

1. O dono precisa entregar sua senha do Mercado Pago ao BarberApp?

Não. No OAuth, ele autentica diretamente no provedor e concede acesso limitado. Nosso servidor recebe tokens após validar o retorno.

2. Qual a diferença entre state e PKCE?

State relaciona o retorno à tentativa iniciada e ajuda a prevenir vinculação indevida. PKCE protege a troca do código, exigindo o verifier correspondente ao challenge.

3. Por que não aceitar RedirectUri enviado pelo navegador?

O retorno precisa ser estático e controlado pelo servidor, correspondendo ao cadastro no provedor. Uma entrada livre permitiria redirecionar dados para destinos indevidos.

4. Gerar a URL significa que a conta já está conectada?

Não. Faltam consentimento, callback válido, troca de código e armazenamento seguro dos tokens.

5. O dinheiro será dividido entre barbeiros?

Não. A única conta recebedora é a do dono. O repasse aos profissionais é administrado por ele fora do BarberApp.

6. Qual evidência permite avançar do teste para a implementação?

O RED funcional: os testes precisam executar e falhar devido à ausência do comportamento esperado. Bloqueio de DLL não é esse RED. Obtivemos 14 falhas por 404 no WSL antes de criar a rota; depois, os 74 testes passaram sem mudar a especificação.

7. Por que o verifier não aparece na URL?

Ele é privado e fica no servidor. Enviamos somente o challenge: SHA-256 dos bytes ASCII do verifier, codificado em Base64URL. Na troca de tokens, implementada posteriormente, o servidor apresenta esse verifier ao provedor.

8. O que acontece com a tentativa quando a API reinicia?

Ela se perde, porque está em IMemoryCache e não no banco. O dono precisará iniciar novamente. O futuro callback deve rejeitar tentativas desconhecidas, expiradas ou já usadas, com testes escritos antes.
