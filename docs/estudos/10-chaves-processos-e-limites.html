Guardar o token não basta: precisamos conseguir lê-lo amanhã

22/10/2026 · Material offline. Seis testes de caracterização aprovados desde a primeira execução. Suíte completa WSL: 197 aprovados, nenhuma falha ou teste ignorado. Diff aguardando revisão humana. Não é certificação da instalação Windows.

Três coisas diferentes

API key: identifica o consumidor, enviada em X-API-Key. JWT: identifica o usuário e suas permissões. Chaves do Data Protection: protegem os tokens recebidos do Mercado Pago antes de armazená-los no banco.

Perder o segredo da API key exige substituí-lo nos consumidores. Perder as chaves de criptografia pode impedir ler tokens já armazenados. Um backup somente do banco não resolve essa perda.

O que verificamos juntos

O mantenedor criou backup do PostgreSQL local, aplicou as duas migrations e conferiu oito entradas no histórico. A API respondeu 200 com NaoConectado usando API key e JWT Admin. Isso prova o fluxo de consulta, não descriptografia de tokens inexistentes.

O Secret Manager guardou a API key fora do repositório. O UserSecretsId versionado identifica o armazenamento: não contém a chave. User Secrets não criptografa valores em disco e não é cofre de produção.

Dois arquivos de chaves indicaram DPAPI. A pasta mostrou ACL para usuário, SYSTEM e administradores. Não lemos nem copiamos suas chaves. Metadados da pasta não provam que a aplicação usa esses arquivos nem que cada arquivo possui a mesma ACL.

O teste entre processos

O teste cria uma pasta temporária exclusiva. O processo A protege um texto explicitamente fictício, grava apenas o ciphertext e termina. O processo B inicia depois e tenta recuperá-lo. Não há banco, endpoint de diagnóstico ou chamada ao Mercado Pago.

Para ler, o processo B precisa do keyring compatível, da mesma identidade de aplicação e do mesmo propósito. O propósito do recorte é BarberApp.MercadoPago.Tokens.v1. Alterar o propósito não é uma refatoração cosmética: impede recuperar o material anterior.

Na leitura, DisableAutomaticKeyGeneration evita gerar substitutas quando faltam chaves. O teste de pasta vazia exige rejeição e nenhuma chave nova. Uma chave nova não recupera um ciphertext antigo.

Os seis casos

  1. Outro processo com as mesmas chaves, aplicação e propósito recupera o texto.
  2. Outro propósito é rejeitado.
  3. Outra aplicação é rejeitada.
  4. Pasta sem as chaves é rejeitada, sem geração automática na leitura.
  5. Cópia das chaves funciona no mesmo contexto de usuário.
  6. Alteração de um byte do ciphertext é rejeitada.

O programa auxiliar só informa PROTEGIDO, RECUPERADO ou REJEITADO e códigos de saída. Não imprime o texto, o ciphertext nem as chaves. O processo filho não herda as credenciais da sessão.

Por que não houve RED?

Estamos caracterizando uma capacidade já implementada pelo framework, não criando comportamento novo da API. Todos os seis casos passaram de primeira. Não quebramos código de propósito nem chamamos erro de compilação de RED.

TDD continua obrigatório para mudanças futuras da aplicação: especificar o comportamento novo, ver a falha funcional, revisar e implementar. Este incremento é uma prova parcial de tecnologia já existente, não uma nova política operacional de chaves.

O que NÃO provamos

O probe não usa o composition root nem o discriminador real do BarberApp. Ele configura uma aplicação de teste e um keyring isolado. Portanto não é prova end-to-end da API.

A execução observada foi no WSL. Ali as chaves fictícias não são protegidas com DPAPI. No Windows o probe pede DPAPI, mas ainda precisamos executá-lo nesse ambiente. Não desativar proteções do Windows para forçar sua execução.

Copiar chaves DPAPI não garante restaurá-las em outro computador ou usuário. Este teste não simula queda de energia, falha de disco, backup da identidade Windows, armazenamento de segredos de produção ou retomada de pagamentos. Nenhuma conta foi conectada.

Exercícios com respostas

1. Status 200 NaoConectado prova que conseguimos descriptografar tokens?

Não. A consulta não carrega tokens e não há conexão cadastrada. Ela prova autenticação/autorização e consulta local nesse cenário.

2. Por que encerrar A antes de iniciar B?

Para que B não possa depender do cache ou de objetos na memória de A. Ele precisa reconstruir o provider a partir do material persistido.

3. O que muda se trocar o propósito?

A recuperação do ciphertext anterior é rejeitada, mesmo com as mesmas chaves físicas. O propósito é parte do isolamento criptográfico.

4. Por que a cópia de teste não equivale a um plano de desastre?

Ela mantém máquina, usuário e configuração compatíveis e usa chaves fictícias. Não testa recuperação da identidade DPAPI nem das chaves reais em outra máquina.

5. UserSecretsId deve ser escondido?

Não. É um identificador sem credencial. Os valores associados no armazenamento local precisam ser mantidos privados e fora do Git.

6. Se o framework já atende ao requisito, devemos forçar RED?

Não. Registre que é um teste de caracterização aprovado desde a primeira execução. RED deve evidenciar uma lacuna funcional real de uma mudança, não uma falha artificial.

Próximo gate

Revisar estes testes e seus limites antes de propor uma política de keyring para a API. Ainda precisamos de recuperação com a configuração efetiva da instalação e procedimento aprovado de backup. Não alterar caminho, nome da aplicação ou identidade de execução sem avaliar os dados existentes.
