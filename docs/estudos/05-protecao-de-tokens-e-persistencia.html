Tokens protegidos antes de dizer “Conectado”

05/10/2026 — GREEN técnico: 125 testes aprovados, incluindo PostgreSQL isolado. Nenhuma conta real ou cobrança. Diff aguarda revisão; checkout, renovação e desconexão ainda não estão prontos.

Hash não substitui criptografia

O PKCE usa SHA-256 para produzir um challenge: não precisamos recuperar o verifier a partir do hash. Já o access token precisa ser recuperável para futuras chamadas ao provedor. Por isso ele é criptografado, não apenas hasheado.

Data Protection protege o JSON com access e refresh token. O repositório recebe somente o resultado protegido. O banco não contém colunas com os tokens originais; a resposta do callback contém apenas status.

O que é o propósito?

BarberApp.MercadoPago.Tokens.v1 identifica o contexto de proteção. O mesmo provider com outro propósito não consegue abrir o conteúdo: isso evita reutilizar acidentalmente uma credencial protegida em outro fluxo.

Propósito não é senha e pode ser versionado. A chave é secreta, gerenciada fora do banco/repositório. Não apague chaves antigas nem presuma que trocar máquina, usuário ou configuração mantém a leitura das credenciais.

Em Windows com perfil disponível, o padrão usa DPAPI para proteger as chaves em disco. Linux e hospedagem exigem planejamento específico. Nos testes, o provider é efêmero: prova a proteção do conteúdo, não recuperação após reinício ou backup.

Scoped e singleton trabalhando juntos

O store de tentativas permanece singleton e compartilha um lock para consumir state uma vez. O serviço de conexão passa a scoped, assim como repositório e DbContext. Cada requisição recebe seu próprio contexto de banco, sem capturá-lo dentro de um singleton.

O cliente HTTP dedicado usa URL fixa, timeout de dez segundos e não segue redirects. A falha externa é traduzida em código seguro, sem reproduzir o body do provedor.

Uma linha recebedora por instalação

A entidade tem Id=1; a tabela tem chave primária e CHECK exigindo esse valor. Uma nova conexão substitui a existente, não cria uma conta por barbeiro ou Admin. ContaId é o identificador da conta no provedor, não o Id da instalação.

A constraint impede duas linhas, mas não decide qual reconexão concorrente deve vencer. Essa coordenação ainda é um risco a resolver antes de pagamentos reais.

SaveChangesAsync termina antes do status Conectado. Se criptografia, escrita ou driver falharem, o callback devolve 503 com título seguro. Não há retry cego do código OAuth.

Por que testar dois bancos?

InMemory permite testar HTTP, proteção e falhas sem dependência externa. Ele não aplica as constraints PostgreSQL. O teste relacional migra um banco WSL isolado, grava ciphertext e confirma que Id=2 é rejeitado pelo servidor.

Um erro da fixture revelou que usar Guid.NewGuid dentro da criação das opções gera outro banco a cada escopo. A correção fixa um nome por teste, compartilhado entre requisição e leitura de verificação. Não enfraquecemos a asserção de persistência.

Os dados do teste PostgreSQL são revertidos por transação; o schema de teste permanece. A migration não foi aplicada ao banco real. Sua reversão apaga a tabela: nunca executá-la com credenciais existentes sem backup e aprovação.

Exercícios com respostas

1. Por que não guardar só o SHA-256 do access token?

Porque precisamos recuperar o token para enviá-lo ao provedor. Hash é unidirecional; proteção criptográfica com chave permite recuperação autorizada.

2. A criptografia no banco basta para produção?

Não. É necessário proteger e persistir as chaves, restringir acesso, planejar backup/recuperação, evitar vazamento em logs e implementar renovação/revogação.

3. Por que o serviço deixou de ser singleton?

Ele passou a depender de repositório e DbContext scoped. O lock compartilhado foi separado em um store singleton, preservando consumo único sem compartilhar DbContext entre requisições.

4. O que acontece se o provedor emitir tokens, mas a gravação falhar?

A API não declara conexão, não devolve tokens e a tentativa já foi consumida. Pode ser necessário revogar a autorização no provedor e começar novamente; compensação/revogação automática ainda não existe.

5. Como provar que a proteção não é apenas uma string diferente?

O teste recupera o conteúdo com o propósito correto e confere os tokens fictícios. Com propósito errado, a operação deve lançar CryptographicException.

6. Por que não aceitar um teste verde sem PostgreSQL?

Ele não prova que a migration ou CHECK funcionem no provedor real. O teste relacional é ignorado quando o ambiente não é configurado; esse skip deve ser informado, não escondido.

7. Conectado significa que o cliente já pode pagar de verdade?

Não. É apenas o resultado da conexão OAuth persistida. Preferências Checkout Pro, webhook, atualização segura do pagamento e jornadas do frontend ainda precisam ser implementados e testados.
