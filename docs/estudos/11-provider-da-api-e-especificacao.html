Testar o componente não é testar a composição da aplicação

22/10/2026 · Implementação do auxiliar após aprovação dos testes, mantidos intactos. Suíte final WSL com PostgreSQL isolado: 201 aprovados, nenhuma falha ou teste ignorado. Build sem avisos/erros e formatação do recorte aprovada. Nenhum código da API foi alterado; diff final aguardando revisão.

A evidência nova

O mantenedor habilitou temporariamente logs informativos de Data Protection. A própria API informou uso da pasta padrão do perfil Windows e DPAPI para proteção em disco. Isso liga a pasta inspecionada à execução observada; ainda não prova recuperação de ciphertext após reinício.

O ajuste de log foi apenas na sessão do PowerShell. Não precisamos imprimir segredos, XML das chaves ou configuração de conexão.

O que muda em relação ao estudo 10?

Antes, o auxiliar criava DataProtectionProvider diretamente e escolhia um nome de aplicação fictício. Agora ApiProbeFactory inicia o entry point real via WebApplicationFactory; ApiProtectionScenario resolve IDataProtectionProvider no contêiner montado pelo Program.cs. Esse contêiner é o composition root: o lugar que conecta os serviços e suas dependências.

O diagnóstico troca só dependências externas por equivalentes de teste: banco InMemory, configuração fictícia e diretório temporário das chaves. Não troca o provider por um efêmero nem define nome de aplicação para mascarar o comportamento padrão. Não executa a API com segredos reais.

Os quatro comportamentos especificados

  1. Processo A protege e termina; B usa mesmo content root, keyring e propósito e recupera.
  2. Com as mesmas chaves, outro content root deve isolar a aplicação e rejeitar o texto.
  3. Com mesmo root, outro propósito deve rejeitar o texto.
  4. Sem as chaves, a recuperação deve falhar sem gerar substitutas.

No padrão ASP.NET Core atual, content root participa da identidade de isolamento. A API ainda não define nome explícito. Não mudar isso como detalhe cosmético: pode tornar tokens anteriores ilegíveis.

Saída verificável, sem segredo

O contrato exige JSON com exatamente quatro campos: origem, status, processoId e identidadeHash. A origem deve ser ApiServices; o hash representa o discriminador da aplicação, não uma chave de criptografia.

O teste confirma o ID do processo filho e compara hashes entre roots. Nenhum payload ou material de chave deve ser impresso. O limite de 30 segundos protege contra travamento; a ordem depende de aguardar o término, não de sleep.

O que as falhas iniciais realmente diziam?

Antes da aprovação, o auxiliar só aceitava proteger/recuperar do componente isolado. Os testes novos enviavam api-proteger/api-recuperar e recebiam código 2, de modo não suportado. Todos falhavam nessa primeira etapa; nenhum chegava a testar a criptografia da API.

Era uma especificação pendente da ferramenta de diagnóstico, não RED funcional do BarberApp e não prova de bug no .NET. Após a aprovação, implementamos o auxiliar sem alterar o teste; os quatro casos passaram e a suíte atingiu 201 aprovações.

Erro de infraestrutura não deve ser vendido como rejeição criptográfica: só Unprotect pode produzir código 3 com status Rejeitado. Falhas do host continuam código 5, sem publicar detalhes internos. Não mudamos a API para compensar falta de infraestrutura.

Leia o código por responsabilidade

Program.cs do auxiliar: reconhece os modos novos e delega; os dois modos antigos continuam funcionando e seus seis testes permanecem aprovados.

ApiProbeFactory: inicia a composição da API, usa ambiente ProtectionProbe, desabilita bootstrap e conexão Mercado Pago, remove fontes de configuração privadas e logs, troca PostgreSQL por InMemory e isola a persistência das chaves. Na leitura, DisableAutomaticKeyGeneration evita substitutas. No Windows solicita DPAPI para as chaves fictícias; o WSL não valida esse branch.

ApiProtectionScenario: pede provider e opções ao contêiner por GetRequiredService. Obtém o discriminador, calcula apenas seu hash, protege o texto fictício ou tenta recuperá-lo. A mensagem final não contém o texto nem a chave.

Build: o auxiliar agora referencia a API e as bibliotecas de teste nas mesmas versões já usadas. A cópia para ProtectionProbe permite só DLLs e metadados de runtime/manifest, não appsettings. Não limpa cópias antigas; a conferência usou configuração nova nos dois projetos, sem apagar arquivos.

Onde termina a prova automática?

Ela usa pastas e chaves fictícias. O agente não acessou o keyring Windows, Secret Manager ou banco local. Ainda será necessária execução operacional explícita no Windows, com provider da instalação, mesma identidade/contexto e geração automática desabilitada para não criar ou rotacionar chaves reais. Não execute os modos atuais apontando para suas chaves reais: api-proteger gera material quando necessário e não é o contrato dessa prova operacional.

Não criamos endpoint público. Não é teste de conta Mercado Pago, pagamento, crash de disco ou restauração de backup. Produção continua desabilitada e o gate de recuperação permanece aberto.

Exercícios com respostas

1. Por que resolver o provider pelo contêiner?

Para usar o serviço que a API registra, em vez de provar apenas que outro provider, criado manualmente, funciona.

2. Mesmo keyring sempre permite recuperar?

Não. Identidade da aplicação e propósito precisam ser compatíveis, e as chaves protegidas em disco precisam ser acessíveis no contexto correto.

3. O que provava o código 2 da fase inicial?

Que o auxiliar não suportava o modo pedido. Não provava falha da API, falha DPAPI nem rejeição criptográfica. Depois de implementar o modo aprovado, os testes passaram sem alteração.

4. Por que não fixar SetApplicationName no teste para passar?

Porque esconderia o efeito do content root e deixaria de especificar o isolamento padrão atual da aplicação.

5. Por que não criar chaves na leitura?

Chaves novas não recuperam o texto antigo e poderiam alterar o ambiente real durante um diagnóstico.

6. Podemos cobrar após esses quatro testes?

Não. Estão aprovados no WSL com dependências isoladas. Não certificam o perfil Windows, recuperação de backup nem a integração de pagamentos.
